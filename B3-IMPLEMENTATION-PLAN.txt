B3 IMPLEMENTATION PLAN
=====================

Scope
-----
Implement B3 only, based on the Setu App Build Frontend and Backend Task Plan
PDF. Preserve existing B1 and B2 APIs and behavior. Do not implement frontend
features, WebSockets, or the Setu Guide AI service itself.

No B3 implementation changes have been made. This file records the proposed
plan for review.

1. CHATS
--------
Add connection-scoped chat and message storage, reusing existing authentication
and connection-membership checks.

Endpoints listed in the project PDF:

GET /chats?filter=
    List chats and include unread counts.

GET /chats/:id/messages?cursor=
    Return messages using cursor-based pagination.

POST /chats/:id/messages
    Send a validated text message.

POST /chats/:id/read
    Mark messages as read for the authenticated user.

PUT /chats/:id/mute
    Mute or unmute the chat for the authenticated user.

Proposed contract details where the PDF does not specify exact values:

- Supported filters: all, active, new, muted.
- "new" means chats with unread messages.
- "muted" means chats muted by the current user.
- "active" means chats not muted by the current user.
- Send-message body: { "text": "..." }.
- Mute body: { "muted": true }.
- Default page size: 30 messages.
- Message pages will be returned oldest-to-newest within each page and include
  a nextCursor when more messages are available.

Chat state and unread counts will be exposed through chat endpoints without
changing existing B1 connection response fields.

2. SETU GUIDE BRIDGE
--------------------
Implement the backend bridge endpoint POST /guide/chat only. Do not implement
the AI service.

The bridge will:

- Require authentication and verify that the user belongs to the connection.
- Derive user ID, match ID, and current journey stage on the server.
- Validate the optional intent, message (maximum 500 characters), and topic
  (maximum 100 characters).
- Return the service response fields specified by the PDF:
  intent, reply, questions, chips, sources, safety, and fallback_used.
- Apply per-user rate limiting.
- Log only request status and timing, not message text or private data.
- Never send private reflection answers, exact date of birth, income, or contact
  details to the service.
- Return a friendly fallback if the service is unavailable.

Required external configuration is not available in the repository:

- Setu Guide staging base URL.
- Endpoint path if it differs from /guide/chat.
- Whether authentication is required.
- If required, credential type and required authentication header/scheme.
- Confirmation that the staging service is available for testing.

No service URL or credential will be invented. Proposed environment variable
names are SETU_GUIDE_BASE_URL and, only if required by the service,
SETU_GUIDE_API_KEY. There will be no default URL or credential. Live staging
verification cannot be completed until the service details are provided.

3. PROFILE AND PARTNER PREFERENCES
----------------------------------
Add the following endpoints:

PATCH /me/profile
    Update only the authenticated user's profile.

GET /me/preferences/:section
    Read a preference section for the authenticated user.

PATCH /me/preferences/:section
    Update a preference section for the authenticated user.

Use the existing profile preference sections:
basic, lifestyle, family, values_outlook, and additional.

Validate profile fields, types, lengths, and section names. Reject attempts to
change profile ownership or another user's data. Preserve existing
GET /me/profile and GET /profiles/:userId behavior.

The PDF does not define the exact preference field schemas. Proposed behavior
is to accept validated object payloads for each existing preference section
and document the supported shapes and examples.

4. STAGING PREPARATION
----------------------
- Support a host-provided PORT and add health/readiness support.
- Use environment variables for service URLs and secrets.
- Add graceful startup and shutdown behavior appropriate for staging.
- Do not read, edit, or commit .env or credentials.
- The repository does not specify a hosting provider, staging project, or
  deployment credentials, so deployment preparation is possible but an actual
  deployment requires those details.

5. DOCUMENTATION
----------------
Update backend/API.md with all B3 endpoints, validation rules, request and
response examples, environment variable setup, and staging instructions.
Document any contract details selected where the PDF is unspecified.

DEPENDENCIES AND CONFIGURATION
------------------------------

- Rate limiting: express-rate-limit is not currently installed; proposed for
  per-user Setu Guide rate limiting.
- HTTP client: no new package is proposed if the deployment uses Node.js 18 or
  newer, which provides built-in fetch. The current package does not declare a
  Node.js engine requirement; documenting or enforcing Node.js 18+ is proposed.
- Setu Guide staging URL and authentication details are missing.
- Deployment provider/project and staging access details are missing.
- Chat filter semantics, message length, exact payload shapes, pagination
  defaults, and preference schemas are not fully specified by the PDF. The
  defaults proposed above will be documented unless revised during review.

COMPATIBILITY AND EXCLUSIONS
----------------------------
- Preserve all B1 and B2 APIs and response fields.
- Reuse existing authentication, connection-membership checks, and response
  conventions.
- Do not change the B2 journey stage source of truth.
- Do not implement frontend functionality.
- Do not implement WebSockets.
- Do not implement the Setu Guide AI service.
- Do not invent external URLs, credentials, or deployment details.

APPROVAL GATE
-------------
This is a plan only. No B3 code should be changed until the user reviews and
approves the plan. Provide the missing Setu Guide staging URL and authentication
